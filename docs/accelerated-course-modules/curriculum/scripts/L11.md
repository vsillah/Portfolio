## Scene 2 · 01:40–03:20 · Trace the failed test
**Source:** Ch17, “The Test That Failed (And Why That Was Fine),” “The Questions That Changed Everything” (`c020.xhtml`). **Avatar:** off. **B-roll:** book-story test card with hypothesis, trigger, review, and revised question; no quoted success metrics. **Delivery:** Keep the failure as learning, not a victory montage.

**Visible copy:** `A failed test can still answer a question`.
```narration
The book gives Sam a test that fails. The team's learning plan had already said what result would make them change course, so the failure did not have to become a debate about whether the work counted. They could ask what the result meant and choose the next question. Notice what that requires. The original hypothesis must still be visible. The trigger cannot be rewritten after the result. Someone must inspect the evidence rather than accept a summary alone. The decision and its reason need to survive the meeting. In our membership exercise, imagine the new first-task card is tested and people still ask staff for help. That is a conditional branch, not a result. The team might learn that the instruction is unclear, or that the task itself is unfamiliar. The observation notes would need to distinguish those explanations. If participants understand the card but cannot tell whether the action worked, confirmation becomes the next test. If recruitment fails, the study is inconclusive. The file should preserve all three routes without pretending that one happened. Sam's story shows an operating habit: a team can be wrong about a solution and still be disciplined about learning. The record is what lets the next meeting start beyond the last one.
```

## Scene 3 · 03:20–05:00 · Connect signal, insight, test, decision
**Source:** Ch18, “Rethink AI as Your Systems Architect,” “Connect AI Across the Build-Measure-Learn Loop” (`c021.xhtml`). **Avatar:** A02, 03:20–03:45. **B-roll:** book's exact arrow sequence as text labels, then a synthetic member-feedback ledger; no invented book figure. **Delivery:** Distinguish each handoff.

**Visible copy:** `Signal → Insight → Test → Decision → Repeatable Momentum`.
```narration
Chapter Eighteen moves from scattered tools to a connected system. Its arrow sequence begins with signal, then insight, test, decision, and repeatable momentum. A signal is a traceable observation, such as a set of first-task notes with source IDs. An insight is an interpretation: perhaps members cannot tell which action starts the service. That interpretation still needs a counterexample and a person willing to challenge it. A test turns the interpretation into a question that can be answered. The learning plan specifies who participates, what counts, and when the result is reviewed. A decision says what the team will do in light of that evidence. Repeatable momentum means the next person can find the record and use it without rebuilding the whole argument. In our synthetic workflow, feedback note F04 reaches the ledger. The reviewer groups it with similar notes, preserves the contrary case, and writes a proposed job. The owner chooses a small card test. The result, when one exists, returns to the decision file with a date and next move. This path is still a proposal until a team names its owners and review gates. Draw each arrow only after naming its input, owner, and output. A line between boxes is not a handoff unless someone can tell when the work crosses it and what happens when it does not.
```

## Scene 4 · 05:00–06:40 · Put a person at the review gate
**Source:** Ch18, “Your Core AI Stack,” “How to Start: The Minimum Viable Stack,” “The Real Goal: Build a System That Remembers” (`c021.xhtml`). **Avatar:** off. **B-roll:** synthetic workflow diagram with human review between suggested insight and decision; course-kit Learning System Loop identified in protected notes as a tactical aid. **Delivery:** Name the limit of automation clearly.

**Visible copy:** `Automate movement; review meaning`.
```narration
The book names tools that can collect, translate, and route information. The trap is to connect them and call the system complete. If an AI summary misreads a member's sentence, faster routing only spreads the mistake. In this course, automation may move an approved note into a ledger, flag a possible pattern, or remind an owner that a review date has arrived. A person checks the raw source, contrary evidence, privacy boundary, and decision consequence before a proposed insight becomes a team commitment. That review gate needs a named owner and a visible way to reject or correct the suggestion. For the fictional membership service, a coordinator could review the source IDs before the pattern reaches the product owner. If the note contains private information, it stays in the protected research system and only an approved summary travels onward. The book's minimum viable stack is about connecting the work, not collecting every tool on a shelf. Choose the smallest path your team can actually maintain. Write what happens when the reviewer is unavailable. Does the item wait, move to another authorized owner, or expire? A silent automated approval would change the decision boundary. The loop should make that boundary plain enough for a new teammate to follow.
```

## Scene 5 · 06:40–08:20 · Give the next person the memory
**Source:** Ch18, “The Real Goal: Build a System That Remembers,” “How to Start: The Minimum Viable Stack” (`c021.xhtml`); Ch17, “What Changed (The Invisible Infrastructure)” (`c020.xhtml`). **Avatar:** A03, 06:40–07:05. **B-roll:** synthetic decision-memory record with original bet, evidence links, result state, and next owner. **Delivery:** Make the record feel useful to a busy colleague.

**Visible copy:** `What we believed · What we saw · What we decided`.
```narration
Imagine joining this work six weeks later. You should be able to answer three questions without searching through a long chat. What did the team believe? What did it observe? What did it decide? The record needs the original hypothesis, the test version, the source links, the measure and guardrail, the reviewer, the decision date, and the next owner. If the evidence is inconclusive, write that plainly. If a later team repeats the test in a different setting, it should keep the earlier result rather than overwrite it. Chapter Eighteen calls the real goal a system that remembers. Memory here is operational: it keeps a small decision from becoming a rumor. Sam's changed meeting in Chapter Seventeen depends on this kind of continuity. In our exercise, a record might say the first-task card remains untested because observation capacity was unavailable. That is not a failure dressed up as success. It is a clear state and a next action. Another possible record could say the test ran but the result is awaiting human review. Neither should be described as an outcome. Keep source links in the authorized system, not on a public slide. The audience-facing card can show the shape of the record with fictional values.
```
