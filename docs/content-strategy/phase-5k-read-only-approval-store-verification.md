# Phase 5K: read-only approval-store verification

`lib/attributable-calibration-approval-store.ts` performs only bounded SELECTs from `public.attributable_calibration_integration_receipts` and its `agent_approvals` parent. It reads by exact receipt ID and by the store's unique report/case/artifact/repair scope, so a conflicting row cannot be hidden by an exact-ID lookup. A missing, duplicate, conflicting, revoked, superseded, or changed parent blocks verification. The module never invokes the receipt-recording RPC.

`lib/attributable-calibration-approval-verification.ts` checks the complete owning-store snapshot against an exact caller-supplied authority payload and retained source fixture. It recomputes a canonical JSON SHA-256 over the payload excluding `receipt_sha256`; this is a stricter read gate because the Phase 5K-A recording RPC stores the supplied digest without calculating it. Future receipts must use this digest convention to pass Phase 5K. It checks all twelve version/hash pairs, receipt and reviewer identity, the single synthetic-review decision, channel and format, parent approval, decision and source expiry, retained response hash, source version and path, privacy and rights, exclusions, provenance, and rollback metadata. The sole store decision authorizes a synthetic review candidate, so historical fixtures remain blocked until their separate source approval store can be verified. No historical fixture is promoted to a production packet or label.

The result is deterministic, scoped to internal read-only review, and has compile-time `false` locks for production writes, packet linkage, label promotion, notification, policy changes, and external actions. A blocked result does not expose a receipt ID. The caller must derive its expected report, policy, case, artifact, evidence, content, cohort, performance, source, and repair bindings from the exact Phase 5F–5J inputs; a matching store receipt alone does not prove that a separately supplied report or packet is current. Phase 5J still permits only a synthetic staging candidate and requires its own exact replay and repair-review checks. Phase 5K does not call that candidate builder or change its authorization semantics.

The staging store contained zero rows before and after this work. The passing case in the unit matrix is a synthetic SELECT-shaped snapshot; it is not a real issued approval. No staging or production receipt was created, no migration was applied, and no live source was collected. A real authority verification remains unavailable until an exact approved receipt exists in the owning store and its source and report bindings can be supplied for read-only evaluation.
