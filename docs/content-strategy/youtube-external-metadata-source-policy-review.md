# YouTube external creator metadata: source class policy proposal v1

**State:** review only; not an approved `SourceClassPolicy`, privacy/rights receipt, or source freshness receipt. Researched 2026-11-26 23:14 ET (2026-11-27 04:14 UTC). This is an operational reading of primary sources, not a legal opinion. It changes no runtime policy or production record.

## Decision

Portfolio may **propose** a version-bound observation receipt for a bounded set of public YouTube Data API metadata without each creator's specific permission, subject to YouTube API terms, the API client's privacy notice, and deletion/refresh duties. That is narrower than approval to retain, score, aggregate, publish, or reuse media. The current Jev packet remains **blocked** because the actual provider response bytes were not retained, the specific API client terms/privacy configuration and owner approval have not been verified, and the intended cross-creator normalized scoring conflicts with the general Developer Policies unless an applicable YouTube amendment or written permission resolves it.

## Proposed source-class contract

1. `source_class=external_creator`, `platform=youtube`, `format=shorts_candidate`. The source is the exact Data API endpoint and canonical public object URL, not a page scrape or an owned Jev asset. Record API project identity privately, HTTP status, `part` list, observation instant/window, video ID, channel ID, public status, and whether each included/excluded row passed the approved identity and format checks. Preserve every exclusion and reason; never silently replace an identity or count.
2. Bind each row to the exact unmodified response **byte** SHA-256 and a separate canonical parsed-response SHA-256, then bind the collection receipt, cohort file hash, content/calendar IDs and versions, policy version/hash, and the approval-store receipt. These hashes have different meanings; a body hash cannot be recomputed from a summary. The current packet has per-response reported hashes but no retained bodies, so integrity remains unverified and `raw_response_sha256=null` for an issuable policy receipt.
3. A source owner may propose a shorter operational freshness interval only after a documented use-specific review. Any issued `expires_at` must be explicit, tied to an exact observation and policy authority, and no later than the applicable API-data retention/refresh boundary. It must also account for an earlier deletion, status change, privacy concern, source drift, or terms change. The 30-day outer limit does not itself create the date. `expires_at=null` blocks use until the owner issues and verifies a bound receipt. An accepted derived-metrics amendment would require its own project-specific version and would not automatically extend other metadata beyond 30 days.
4. Keep a privacy determination and a rights determination as **separate** signed/approved receipts. A fact's copyright status cannot substitute for privacy or platform permission. Approved owned-Jev receipts cannot cover external creators. A receipt candidate can list gaps but cannot self-approve; verify authority identity/version and policy digest in the owning store.
5. Preserve audit events for observation, field changes, inclusion/exclusion, authority review, refresh, revocation, purge, and rollback. Record prior/superseding receipt IDs and hashes. On drift, revoke the current use binding, quarantine the affected row and any derived cohort, and delete or refresh API data according to the applicable policy. Keep only a compliant minimal tombstone/audit reference if counsel/platform review permits it; a hash is still a source-derived identifier in context.
6. Human QA remains pending on the Jev thumbnail/content package. Policy review is a separate gate. No metadata receipt may bypass source evidence, outlier, privacy, rights, Human QA, or external execution locks. No live read, policy activation, evidence linkage, media generation, notification, upload, scheduling, publication, provider action, or production write follows from this proposal.

**Conflict rule:** API Terms §2.4 states that the API Terms prevail over contradictory agreement documents. The extra metrics page appears to offer an acceptance-based amendment to the general derived-metric/retention rules, but no accepted amendment for this API project is in evidence. Treat it as unresolved, never as a silent override. Recheck the official texts, revisions, privacy notice, approval-store authority, and accepted project terms before an owner can activate any source-class policy.
