## Boundary

The current `youtube-readonly-evidence-acquisition-v2` bridge makes bounded provider reads, may return unscored observations, and does not persist a cohort. No retention job can be run against a cohort that does not exist. This design applies only if a separately reviewed future version proposes persistence. The candidate source class is third-party public YouTube API metadata described in [source policy](youtube-external-metadata-source-policy-review.md). Connected AmaduTown channel data, OAuth tokens, comment inboxes, owned media, and existing calendar/content rows are separate stores and must not be swept by this path.

The [compliance dossier](youtube-derived-metrics-compliance-dossier.md) and its [review addendum](../../artifacts/research/youtube-derived-metrics-compliance-dossier-2026-11-27/review-addendum.md) remain controlling gap inventories. No accepted project-specific derived-metrics amendment, privacy/rights approvals, or issuable raw-byte provenance receipt is in this design. `collection_enabled=false`, `persistence_enabled=false`, `scoring_enabled=false`, `evidence_linkage_enabled=false`, and `external_actions_enabled=false` remain fixed until separate authority and implementation reviews.

## Proposed record and clock contract

Each future row needs a store-owned opaque row ID and `source_class=external_creator`, `platform=youtube`, canonical video/channel IDs and URL, exact endpoint and requested `part` set, response HTTP status, source public status, response-byte SHA-256, separate canonical parsed-response SHA-256, collection receipt identity, policy version/hash, privacy and rights decision identities, approval-store identity, source/content/calendar versions if applicable, and inclusion/exclusion reason. Never put credentials or raw response bodies in a receipt or log. A hash is not a substitute for retained bytes when independent byte verification is required. A separately authorized byte store must have its own retention and purge path; no indefinite raw response archive is implied here.

`observed_at` is the UTC instant at which the provider response body finished arriving in the collecting process, from a trusted server clock. Capture it per response, before parsing; do not substitute video publication time, job start, database insertion, receipt creation, client time, or a prior cached response. If the clock is untrusted, missing, future-dated beyond approved skew, or the response boundary cannot be established, quarantine and block persistence/use. Store the original instant immutably. For a multi-response cohort, each row has its own clock and the cohort's deadline is the earliest member deadline.

For non-authorized API data, `retention_deadline_at = observed_at + 30 calendar days` in UTC, with an earlier provider, privacy, rights, deletion-request or source-policy deadline taking precedence. A conservative job target must be earlier than the deadline, with margin for retry and outage. This deadline is a **storage delete-or-refresh ceiling**, never a source freshness grant. `use_expires_at` is separately issued by a verified authority for the exact observation and may be earlier; null blocks all use. Neither clock can be silently extended by a job retry, a DB touch, a returned API hash, or a cohort edit.

## State machine and atomicity

| Event | Required state and operation |
| --- | --- |
| Proposed observation | Quarantine until exact API project/client, public object/field minimization, separate privacy and rights decisions, policy digest, source bytes, and time are verified. Excluded, private, unlisted, deleted, hidden-required-count, identity-mismatched, or unsupported fields never enter the usable cohort. Record exclusion reason without preserving prohibited payload. |
| Valid refresh before deadline | A separately authorized GET produces a **new** observation ID, clocks, response-byte and parsed hashes, status and decisions. Verify full identity and authority again. In one transaction supersede the old use binding, install the new eligible version, and enqueue old API bytes/fields for bounded purge. Never mutate the original observation or copy its approval to the new one. A changed or missing object revokes use and goes to deletion, not an invented zero/null update. |
| Deadline or verified deletion request | Revoke use first, block every reader by state and deadline, then delete the scoped API fields, raw bytes, derived cohort/cache copies and search/index projections. A request for public metadata uses the published `/legal/data-deletion` email path; verify scope and requester claims without requiring a connected channel. A subject request can impose an earlier deadline. Do not delete YouTube-held data or unrelated connected-channel records. |
| Drift, outage, failed refresh, or failed purge | Fail closed: revoke/quarantine immediately; do not serve stale data, retry external GET automatically, infer an extension, or mark complete. Queue an internal recovery record with bounded retries, owner, next check, deadline and exact failing step. Escalate before the deadline; if expiry arrives, deletion remains required. A failed delete is an incident requiring recovery evidence, not a successful tombstone. |
| Rollback | Revert code/config by normal deployment controls while the stored row stays revoked. Do not restore purged API data or resurrect an old receipt from backup. Reconciliation after rollback must scan for orphaned rows, cached copies and overdue deadlines before reopening any reader. |

The sweep takes a lease scoped to `(source_class, row_id, observation_version)`, uses compare-and-swap on state/version, and records a stable idempotency key for each transition. Repeated runs over unchanged state are no-ops and do not duplicate receipts, refresh calls, notifications or retry counts. A new material source/version change gets a new key. For refresh, replacement insert and old-binding revocation must commit atomically; purge can be a separately acknowledged step while **both** versions remain unavailable if purge fails. Never let a partially refreshed row become usable. All read paths enforce state, `use_expires_at`, and retention deadline independently of the sweep.

An immutable event receipt records event type, source/observation version, prior and successor IDs, policy and approval digests, clock values, transition idempotency key, deleted-store inventory, verification result and actor/service identity. It contains no credentials or prohibited source fields. Correction is an appended superseding event, never an edit. After purge, retain only the minimal non-reversible audit tombstone that a separate legal/platform determination explicitly permits; source IDs and hashes can remain identifying in context and are removed if that determination is absent. Keep the sensitive immutable event in a separately governed audit store only if that retention is authorized. No receipt in this packet is an issued production policy receipt.

## Proof required before a future implementation can ship

1. Create a migration and rollback plan in a separate lane. Define every physical copy: primary row, raw-byte object, cache, backup, index, export and derived calculation. A copy without a bounded deletion mechanism blocks persistence. Backups need a documented expiry and non-resurrection restore procedure.
2. Use synthetic fixtures and approved read-only historical records for a dry run. Capture before/after IDs, versions and counts for the exact external-cohort namespace **and** `social_content`, `social_content_calendar_items`, connected-channel configuration, unrelated source classes and existing approval receipts. Require unchanged checksums/counts outside the scoped external cohort. Do not use aggregate count equality alone: compare sorted IDs/version digests so delete-plus-insert cannot hide a mutation.
3. Test clocks at 29 days, exactly 30 days and overdue; earlier requests; missing or skewed time; private/status drift; changed hash; failed provider read; partial purge; retry; concurrent sweeps; restore; and a request naming a public URL without a connected account. Prove readers fail closed even if the job is down. Verify the old raw bytes and every projection disappear after a successful purge, and no stale reference can relink them.
4. Require a reviewed security/privacy report covering field minimization, credential redaction, authorization separation, request handling, audit minimization, rights and provider policy. Require staging synthetic proof and explicit production-change authority as applicable before any migration, job, provider request or data write. Human QA is needed only if a client-facing surface changes.

The local [synthetic trace](../../artifacts/research/youtube-retention-review-2026-11-27/synthetic-retention-trace.mjs) tests the state contract and ID/count invariants without a provider, database, secret, deployed route or external action. It is a design demonstration, not evidence of a live purge.
