# App Activation Control Plane

Status: Phase 1 source foundation, Phase 2 local synthetic operator console, and Phase 3 direct application contracts. The new provider remains disabled by default. No remote migration, provider configuration, invitation delivery, or app integration is active.

Phase 5 adds a source-only, reusable rollout kit in `lib/app-activation-rollout.server.ts`. It adds no route, table, provider configuration, or live entitlement check. Captain source review, focused tests, lint, typecheck, and build are the validation gate; there is no changed client-facing behavior requiring Human QA or an MP4.

## Purpose and ownership

Portfolio owns the reusable adult tester activation lifecycle for Trumpet Trainer and future apps. An app identifies itself with a registered `app_key` and consumes only its own grant. An interest record is not a sales lead, an invitation is not a grant, and neither interest nor consent authorizes external outreach by itself. Existing Portfolio lead and outreach systems remain separate; future intake may link provenance without silently enrolling a contact into sales automation.

Reference review: ReversR SIT's hosted commercial API and `useCommercialization` hook provide the invite, redemption, and grant pattern. Its beta intake n8n export has a webhook, Google Sheet append/update, and Gmail send node. These are reference patterns, not runtime dependencies or proof of enrollment. This design omits ReversR's app-specific plans, credits, billing, profile headers, and returned activation code. The original references remain in their own workspaces; no raw export is copied here.

## Lifecycle

1. **Interest:** Capture an adult contact email, registered app key, source reference, and a separately versioned consent decision. Do not collect child identity.
2. **Review:** A human operator moves `submitted → in_review` and then chooses `approved`, `waitlisted`, or `rejected`. A waitlisted record can return to review. Every decision needs an actor, timestamp, and audit event. Rejection is terminal in v1; a new request is required after reconsideration.
3. **Invitation:** Only an approved interest with current granted `interest_contact` consent may receive an invitation. Generate a cryptographically random token server-side, store only its SHA-256 digest, set a bounded expiry, and transmit the raw token only in the authorized delivery path. Never put it in an operator list, log, analytics event, or read model.
4. **Redemption:** An authenticated adult account must match the interest email. The private database function claims an issued, unexpired invitation by app key and digest with a conditional update. It creates one app-specific grant and audit events in the same transaction. A concurrent or repeated call returns no grant. The server must hash the supplied token and verify its authenticated caller before invoking the function; the function also checks the account email.
5. **Access:** The consuming app checks `app_key`, `auth_user_id`, `revoked_at is null`, and `expires_at > now()` for every entitlement decision. Revoking an invitation only stops an unredeemed invitation. Revoking a redeemed user's access changes the grant. An expired grant does not grant access even before an expiry sweep records its event.
6. **Audit and privacy:** Append a source/actor event for each lifecycle step and each consent version or withdrawal. Keep token material out of events. Preserve adult contact consent independently from auth identity and any child-facing profile. No child PII belongs in this control plane.

The tables are in `public` for repo schema convention, with RLS enabled and `anon`/`authenticated` privileges revoked. No client policies exist. Only a trusted server role may use the data; the redemption function is in non-exposed `activation_private` and callable only by `service_role`. Phase 2 must add explicit application authorization, rate limiting, anti-enumeration responses, operator audit, and local RLS/SQL tests before any route is exposed. The server role must never reach a client bundle.

The private function runs as its caller and compares the supplied Auth user ID with the canonical `auth.users.email`. Current Supabase projects do not give `service_role` table SELECT for this invoker query, so the migration grants that server-only role SELECT on exactly `auth.users.id` and `auth.users.email`. It does not grant client roles access to Auth data or change Auth schema ownership. This narrow dependency must be checked again during hosted migration review.

## Source contract

`lib/app-activation.ts` is the product-neutral TypeScript domain contract. The generated migration `20261106234206_app_activation_control_plane.sql` is the local persistence contract. The SQL function is the atomic redemption boundary; the TypeScript redemption predicate is a preflight guard, not a substitute for the database claim. One unrevoked grant per app/account and one grant per invitation are enforced by indexes. Reissue after expiration requires explicit revocation or a future lifecycle design, so Phase 2 must not silently overwrite grants.

## Phase 2 implementation brief: operator review console

The Phase 2 console route is `/admin/app-activation`. Its admin API requires Portfolio's server-side admin verification. The only active repository is a deterministic local fixture enabled by `APP_ACTIVATION_REVIEW_MODE=synthetic` during `next dev`; production and previews return a provider-unconfigured state and reject mutations. Synthetic invitation preparation stores no raw token, hash, or delivery link. Its audit events reset with the development server. Portfolio activation tables are the sole future system of record. Source receipts remain provider-neutral so a separately approved, one-time legacy import could retain provenance; this phase does not read or import a legacy source. No Google Sheets or n8n runtime integration belongs in the target architecture.

Build a private admin route that lists interest by app and state, shows consent version/source and a timeline, and supports review, waitlist, rejection, approval, invite issuance, and grant revocation. Require server-side admin authorization using Portfolio's current auth pattern. Every mutation must validate the lifecycle, write an audit event transactionally, and record actor/reason. Search by adult email with deliberate limits; do not show raw tokens or child identity. Invitation issuance must check current consent, use secure randomness, and return the raw token once only to an explicitly approved delivery adapter. No automatic Gmail/n8n send or sales-lead creation.

Add a separate adult-facing interest and redemption API only after privacy copy, consent version, abuse controls, response enumeration, and app-origin rules are reviewed. Use the private redemption function, then expose only an app-scoped entitlement check. Test concurrent double redemption, expired/revoked grants, role denials, cross-app reads/writes, consent withdrawal, and operator actions in a local database. Confirm the migrated schema and the complete source-to-grant path on synthetic data before proposing any hosted migration. Keep provider activation, recruitment, and any outbound invitation delivery behind explicit authorization.

## Phase 3 direct application boundary

`lib/app-activation-repository.server.ts` is the server-only Postgres boundary. It requires `APP_ACTIVATION_PROVIDER=postgres`, `APP_ACTIVATION_ENABLE_WRITES=true`, a server-only `APP_ACTIVATION_DATABASE_URL`, a JSON app-to-exact-HTTPS-origin map in `APP_ACTIVATION_APP_ORIGINS`, and `APP_ACTIVATION_CONSENT_VERSION`. No setting is supplied or enabled in this change. Connections switch to `service_role` for each transaction and fail if that role cannot be assumed. The additive local migration adds a unique hashed intake replay key and a one-issued-invitation constraint. It is not applied remotely.

`POST /api/activation/interest` accepts the reusable `AdultInterestForm` contract. It requires adult attestation, explicit contact consent, a current consent version, registered app key, exact allowed origin, provider-neutral source receipt, and UUID-shaped idempotency key. The repository normalizes the adult email, writes interest, consent, and audit events in one transaction, and serializes same-key attempts with a database advisory lock. A replay with changed email, receipt, or consent version is rejected. The response makes no account or access claim. The route has a bounded body and per-instance IP rate limit; a distributed edge or provider abuse limit remains an activation gate for hosted use.

`POST /api/activation/redeem` requires Portfolio verified Auth, non-anonymous signed-in user, adult attestation, **Portfolio's first-party origin**, and a one-time token. An app-origin browser request cannot send a Portfolio Auth bearer to this route. The server hashes the token before the private SQL claim. The SQL function checks canonical Auth email, approval, latest consent, app key, expiry, and revoked state; redemption and grant events are atomic. Failed or replayed claims return no grant. The repository never logs or returns token material.

`POST /api/activation/grant` is a server-to-server grant check. It requires an app-specific server secret and an opaque handle obtained through the single-use handoff; it returns only app key and a boolean. It rechecks current grant revocation and expiry on every call. The admin API uses the same repository when configured and otherwise retains the synthetic or unconfigured behavior. Hosted review decisions and revocations are supported by the repository. Invitation issuance requires `APP_ACTIVATION_ISSUANCE_ENABLED=true` and an explicitly selected server delivery adapter. No raw token is shown in a list or read model.

## Phase 6 runtime boundary, source-only candidate

Migration `20261107111258_app_activation_runtime_boundaries.sql` adds private Postgres abuse counters, two-minute single-use handoff codes, and 24-hour opaque app session handles. All three tables are under non-exposed `activation_private`, deny `anon` and `authenticated`, and remain within Portfolio Postgres. The migration is **local source only**; neither staging nor production has been changed. No Google Sheets or n8n runtime is used.

`APP_ACTIVATION_DISTRIBUTED_ABUSE_ENABLED=true` and a server-only `APP_ACTIVATION_ABUSE_SECRET` of at least 32 characters are required before interest, redemption, handoff, exchange, or grant routes become usable. The Postgres counter uses an HMAC of route and client IP, never a raw IP. An unavailable counter fails the request closed. The 15-minute per-key budgets are five interest requests, eight redemption requests, twelve handoff issues, 120 app-server exchanges, and 1,200 app-server grant checks. Server-to-server budgets allow shared egress IPs; they must be reviewed against expected staging traffic. This is a shared database boundary across instances; an edge or WAF limit can add earlier protection. It needs a reviewed retention job for stale counter and handoff rows before activation.

The adult signs in and redeems on Portfolio's own origin. `POST /api/activation/handoff` accepts an app key and an HTTPS return URL whose origin exactly matches that app's allowlist. It verifies Portfolio Auth and an active app grant, then returns a two-minute code in the URL fragment. The app backend exchanges that code once using `POST /api/activation/handoff/exchange` and its app-specific server secret. The response contains an opaque 24-hour handle, not a Portfolio bearer or stable Auth user ID. The app must bind that handle to its own verified adult session server-side, keep it out of browser storage and logs, and call `POST /api/activation/grant` from its backend for current access. A copied code cannot be replayed; an expired code or revoked grant fails. The consuming app integration and Portfolio first-party handoff page remain staging gates.

`APP_ACTIVATION_HANDOFF_ENABLED=true` and `APP_ACTIVATION_APP_SECRETS` (JSON map of app key to a separate, at least 32-character server secret) are additional default-off switches. No secret is supplied by this PR. The existing exact-origin map still owns browser return URLs; an app server secret never authorizes another app's origin or handle.

`InvitationDeliveryAdapter` has a provider-disabled default. The explicit synthetic adapter requires both `APP_ACTIVATION_DELIVERY_MODE=synthetic` and `APP_ACTIVATION_SYNTHETIC_DELIVERY_ENABLED=true`, plus local development or the exact staging project ID binding. It accepts only `example.test` recipients, sends nothing, persists no raw token, and returns a random receipt. It is suitable for contract testing, **not** live invitation delivery. The operator route passes the raw token only to the server adapter and returns a non-secret receipt. If delivery fails, it revokes the just-issued invitation and records a generic audit event; a failed compensation returns an operator-review error and blocks automatic retry. A real provider adapter, outbound authorization, and verified recipient path are still required for live invitations.

The dedicated `APP_ACTIVATION_DATABASE_URL` takes precedence. For the dedicated staging Vercel project only, `POSTGRES_URL_NON_POOLING` may be reused when `APP_ACTIVATION_STAGING_DB_FALLBACK=true`, `APP_ACTIVATION_STAGING_PROJECT_ID` exactly matches `VERCEL_PROJECT_ID`, and `VERCEL_ENV=production`. This explicitly reviewed fallback is default off and must never be enabled on the Portfolio production project. No Vercel environment variable is changed in this PR. Production database selection needs a separate review.

Staging gates: captain migration review and staging apply; verify service-role and RLS grants, counter concurrency, handoff replay and revocation against local or staging Postgres; approve exact origins and consent copy; implement and review the first-party adult page and consuming app backend session binding; provision scoped secrets and retention; select a real delivery adapter only after outbound approval. Activation, billing, provider delivery, and recruitment remain off.

## Phase 5 reusable rollout kit

The `AppRolloutManifest` is a reviewed registration proposal, **not** a second runtime registry. `public.activation_apps` is the app registration system of record, and the existing server-only `APP_ACTIVATION_APP_ORIGINS` map is the runtime exact-origin allowlist. The kit validates app keys, duplicate registrations, exact HTTPS origins, consent version, source adapter commit, adult Auth handoff, delivery status, and default-off switches. Invalid entries or an origin shared by two apps in the runtime map fail the whole map closed. Keep the manifest's approved values aligned with the eventual Postgres row and server configuration; a manifest alone cannot enable either.

The Trumpet Trainer reference manifest binds source adapter commit `1e3f9d23d211552af5c1f42b5cd286919ef1295a`. Its origin list is empty; delivery, distributed abuse control, identity exchange, and app session binding are unconfigured; activation and billing are off. Validation requires all four reviewed runtime controls before activation can be marked enabled. The `interest-v1` field is a source example and needs a separately reviewed consent document/version before any rollout. Do not infer a live origin or readiness from the source commit.

### Adding an app: operator checklist

1. Review the app's source adapter at an exact commit. Prepare a manifest with a unique stable app key, display name, and exact HTTPS origins. Reject paths, credentials, query strings, duplicate origins, and cross-app origin reuse until its ownership is resolved.
2. Approve adult contact and privacy copy and its consent version. Confirm the app sends an adult-only interest request with source receipt and idempotency key; keep child data out of Portfolio activation records.
3. Review the adult Auth handoff and require Portfolio-verified identity at redemption and every grant read. Bind `app_key` and `auth_user_id` on both sides. Register the app in the existing `activation_apps` table only through a separately approved data change, then configure only its reviewed exact origins through the existing server setting.
4. Review a server-side invitation delivery adapter, operator authorization, abuse controls, and one-time token handling. No provider is wired by this kit. Confirm consent and approval before issuance, and verify redemption, expiry, replay denial, and app-scoped grant reads using synthetic accounts.
5. Keep `activationEnabled` false until the provider, migration, app integration, consent, delivery, release, and Human QA gates have separately passed. Revocation must end grant access immediately; revoking an unredeemed invitation must prevent redemption. Roll back by disabling the app rollout/provider and revoking issued grants or invitations through the authorized operator path. Verify that access then fails closed.
6. If paid access is later proposed, review it as a separate project. An activation approval or grant is **not** a paid entitlement. The `activation_and_paid` decision requires both an active app/account grant and a separately read, active, unexpired paid entitlement bound to the same app/account. A paid record alone cannot activate an app. The `AppAccessAdapter` and `checkAppAccess` scaffold fail closed when either read is unavailable. This kit creates no checkout, price, product, webhook, charge, billing table, or paid route.

Portfolio's existing Postgres activation tables are the only activation system of record. Google Sheets and n8n have no runtime or operating role in this rollout. Source receipts may retain historical provenance but cannot become an alternate enrollment or billing authority.
